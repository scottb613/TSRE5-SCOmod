Software Tools
==============

- All v0.9 WIP builds use the Qt 6.11.1 MinGW 13.1 toolchain installed under `Y:\DEVTOOLS\TSREvc\Qt`.
- Configure through `Y:\DEVCODE\VSwork\TSREvc\scripts\Invoke-CMake.ps1` with the `windows-debug-local` or `windows-release-local` preset.
- Standard configure command: `.\scripts\Invoke-CMake.ps1 --preset windows-debug-local`
- Standard build command: `.\scripts\Invoke-CMake.ps1 --build --preset windows-debug-local`
- Do not use the old Qt5/MSYS2 qmake build commands for v0.9.
- Do not call a random `cmake`, `g++`, or `mingw32-make` found earlier on PATH. The local preset selects the matched Qt compiler and vcpkg toolchain.

AI House Rules
==============

- We work in `TSREvcWIP`.
- We work by Git tag numbers.
- If a missing tool would make the work easier, report it before proceeding.
- Git may be polled to determine what has changed and where we stand.
- Before making any significant change, start with a code snapshot for rollback.
- Normal work is done in WIP and the required runtime is handed to `TSREvcTST`.
- Keep `scoRelease_v0.9.txt` updated as the running work log.
- Do not run a full or long application compile unless explicitly requested. Hand the main compile and TST copy task to the operator.
- Small focused builds, CMake configuration, AUTOMOC, and targeted tests are allowed when needed.
- If a completed focused build produces the required executable, copy it and its required runtime files to TST.
- If an open TSRE process blocks an approved TST copy, close only the blocking TSRE process.
- Always clean up task leftovers and failed temporary output when the task is complete.
- Report old code messes when discovered so cleanup can be considered separately.
- Popup dialogs use an orange title. Add subtitles only when the popup contains distinct titled sections; a single-section popup has no subtitle.
- Yes/No confirmation popups use the shared dialog format: Yes has the green acceptance bar, No has the red rejection bar, and destructive decisions default to No.
- No Push Local or Push Git until explicitly requested and the working TST is satisfactory.
- The public v0.8 release remains separate and must not be pushed or changed as part of private v0.9 migration work.

Qt6 Migration Rules
===================

- Preserve v0.8 behavior before improving architecture or graphics.
- Make one migration concern at a time and keep it reviewable.
- Use Eric's `8.006n-QT6-VSCode` branch as the first source/API reference.
- Use Peter's fork as the independent CMake/vcpkg reference.
- Use Goku's TSRE5vc for compressed-texture and later renderer research.
- Never edit a reference checkout or copy a reference tree wholesale into WIP.
- Do not combine Qt6 API conversion, renderer replacement, and source reorganization in one change.
- Do not use Qt Core5Compat as a permanent answer.
- Treat MSTS/Open Rails UTF-16 serialization, terrain painting, seasonal TERRTEX, route saves, paths, and settings recovery as high-risk compatibility areas.
- Native DXT work comes after basic Qt6 parity and must be checked against GenX terrain painting and texture saving.
- Windows 7 is no longer a target. v0.9 targets 64-bit Windows 10 1809 or later and Windows 11.

Push Local
==========

- Do not proceed until "Push Local" or equivalent is explicitly requested.
- Hand the full compile task to the operator unless Codex is explicitly asked to run it.
- Check all changed code for the current release for accuracy, efficiency, and cleanup.
- Check `scoRelease_v0.9.txt`, then update `masterDocs\scoWorkList.txt`.
- Keep HIGHLIGHTS and WORK DETAIL synchronized.
- `masterDocs\scoWorkList.txt` is the master source of release documentation.
- After the master is correct, update other formatted documents containing HIGHLIGHTS or WORK DETAIL.
- In `masterDocs\BBSrelease`, update the respective release document with only the HIGHLIGHTS. Leave earlier release documents in place when the release number changes.
- Build the approved distributable in `dist` with the required executable, runtime libraries, assets, and documents.

Push Git
========

- Do not proceed until "Push Git" or equivalent is explicitly requested.
- Complete every Push Local requirement first.
- Push only the reviewed and explicitly approved branch, tag, source, and release assets.
- Never publish the private migration-start tags as release tags without explicit approval.
